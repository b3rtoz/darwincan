# Design decisions

The decisions that shaped darwinCAN, in the order they were made, each with its reason where the reason is not obvious. This is a record, not a specification: [../design.md](../design.md) describes the result, and [../roadmap.md](../roadmap.md) what is planned.

Add a row when a decision is made that someone might later want to revisit: what was chosen, and why not the alternative.

| Date | Decision |
|---|---|
| 2026-11-11 | Clients retry for 500 ms when the daemon is still starting |
| 2026-11-11 | Tools follow can-utils and `ip link` command lines and output; unsupported options are refused, never ignored |
| 2026-11-12 | Real-time scheduling for the daemon's protocol timer threads and for tools that pace frames |
| 2026-11-12 | Start hardware testing with the classic PCAN-USB rather than wait for a CAN FD adapter |
| 2026-11-13 | Order of work: bench close-out, merge, transmit confirmation, CAN FD on the wire; further backends and programming interfaces after that |
| 2026-11-13 | The public programming interface (C API, python-can) is not planned until the bench tests and transmit confirmation are done, because transmit confirmation changes what a client sees of its own frames |
| 2026-11-13 | Transmit confirmation: a backend reports each frame the adapter says was sent; clients see their frames then, with the adapter's time. Frames still with the adapter when an interface goes down are dropped without an error per frame, as on Linux; an ISO-TP transfer in flight fails with "a frame could not be put on the bus" |
| 2026-11-13 | STmin is a strict lower bound on the bus. ISO-TP waits for the adapter's report of each frame; a correction that made gaps shorter undercut STmin once in 35,000 frames and was dropped |
| 2026-11-13 | The daemon's frame-handling threads run in the real-time class, like its protocol timer threads |
| 2026-11-13 | `cansend` returns once the daemon has taken the frame, as on Linux, and no longer waits for its own copy |
| 2026-11-13 | A stop signal takes hardware interfaces off the bus (at most 2 s), then ends the daemon with the same exit status as before |
| 2026-11-14 | So does the USB library's delivery thread: the daemon makes real-time the thread that appears when it begins to watch for adapters |
| 2026-11-14 | The daemon uses the USB library's version 0.2 (`nusb` 0.2.9) and finds that thread by its name. The daemon needs Rust 1.85; the permissive crates stay at 1.75 |
| 2026-11-14 | The programming interface is versioned, with a protocol version check, but carries no stability promise or packaging yet. Four uses count equally: test automation with timing, diagnostics over ISO-TP, porting Linux tools, logging and replay |
| 2026-11-14 | A C API first, a python-can plugin on top of it afterwards, then the Kvaser backend |
| 2026-11-14 | The C API has the structs and constants of `<linux/can.h>` exactly, and its own `dcan_*` functions in place of the socket calls; no shim that lets Linux source compile unchanged |
| 2026-11-14 | The C API is the `darwincan` crate built as a C library, not a crate of its own, with a hand-written header checked by a C program in the tests. Receive calls take a timeout; an ISO-TP send waits until the message is out |
| 2026-11-14 | Made ready for use the same day: joined filters (`CAN_RAW_JOIN_FILTERS`, and `candump`'s `j`), a receive that a signal ends, an ISO-TP channel one thread can receive on while another sends, `make install` with pkg-config, two example programs and docs/c-api.md. Left out on purpose: `CAN_BCM`, DLC above 8, a socket on all interfaces |
| 2026-11-14 | The protocol version goes up with every change to a message. A daemon answers a client of another version before hanging up, so the client can say what is wrong |
| 2026-11-15 | The broadcast manager before Python, to finish the API. It follows `CAN_BCM` operation by operation and flag by flag, with `struct bcm_msg_head` laid out as on Linux in a header of its own. Its jobs run in the daemon, one real-time thread per client. Where it departs from Linux: a job that cannot send says so once, and one broadcast manager serves one interface |
| 2026-11-15 | Order of work from here: remove the differences from Linux that can be removed, then J1939 (wanted for commercial vehicle networks), then python-can, then Kvaser |
| 2026-11-15 | J1939 as Linux has it, in full (the transport protocols and NAMEs, not only listening and single frames), because a port from Linux needs all of it. The protocol is written from the standards, not from the kernel's GPL implementation, so it can live in a permissive crate. One stack per interface, shared by its sockets, as on Linux: a session to a local address is answered once. A J1939 send is acknowledged by the daemon, unlike a raw send, because only the daemon knows whether a NAME has an address. Address claiming is left to the program, as on Linux |
| 2026-11-15 | python-can next, without waiting for a J1939 reference device; the J1939 tools are planned for after it |
| 2026-11-15 | The Python package loads the installed C library with ctypes and has no compiled part, so it needs no build per Python version. A bus given a `bitrate` brings a down interface up at it (with `listen_only` if asked) and leaves it up when closed; an interface that is already up is shared and never reconfigured, so a different `bitrate` fails the open. Without a `bitrate` the interface is left alone, as on Linux. (First built to only compare, as `socketcan` ignores the option; but that is for want of root on Linux, which does not apply here.) A transmit failure reported after the send is logged and counted by `recv`, not raised, so that a reader thread survives it. ISO-TP is a class of the package's own (`IsoTpSocket`), since python-can has no such thing |
| 2026-11-15 | The Kvaser backend is for the hydra protocol first, since the adapter available for testing (a USBcan Light 4xHS) speaks it. Requests and frames share one pair of endpoints there, so its receive loop runs before the adapter is identified and hands answers to whoever asked. A report that comes with a bus error may only worsen a channel's state: that adapter sends zeros with them. An adapter that cannot be listen-only refuses to be started so, rather than start able to acknowledge |
| 2026-11-15 | An acknowledged request (flush, an option, a J1939 or broadcast manager send) waits for its acknowledgement however short the socket's read timeout: the timeout is for receiving. Found when a flush failed behind a frame that was waiting for room in an adapter |
| 2026-11-15 | A raw socket is told its interface's state by the daemon and refuses to send on one that is down, bus-off or gone, without a round trip; before refusing it asks, in case the news of a change was lost. A send looks for such news at most once a millisecond |
| 2026-11-15 | The descriptor a program waits on is a kernel event queue the library keeps in step with what it holds, not the socket, so that it is readable exactly when a receive would return something |
| 2026-11-15 | Interfaces have an index (not kept across daemon restarts) and a name kept per adapter channel in `~/Library/Application Support/darwincan/interfaces`; `any` is not a name an interface can have |
| 2026-11-15 | An acknowledged request can be refused: the daemon answers `Refused` in the place of `Ok`, and the client matches the answer to its request by order |
| 2026-11-16 | J1939: the receiver of a connection asks again for packets that went missing instead of giving the session up, as SAE J1939-21 (May 2022) has it in 5.10.3.2: at the end of the block it had asked for, from the first missing packet onwards, or after the 750 ms timeout when the end of the block was lost (figure C5). It does not keep the packets that followed the missing one. It asks at most twice for one message, then aborts with reason 5 (5.10.3.2 and 5.12.3; whether the limit counts for a message or for a packet is not said, and for a message is the stricter reading). A sender sends packets again only from the block asked for last (5.10.3.2), and aborts when asked for earlier packets or for packets beyond the next one; the standard does not name that abort, AUTOSAR's "Specification of a Transport Layer for SAE J1939" (R24-11, SWS_J1939Tp_00223) does, and the reason sent is 250, which Table 6 gives for a reason not listed |
| 2026-11-16 | J1939: three places where the transport protocol differed from SAE J1939-21 (May 2022) were found by reading it against the code, and changed. A clear-to-send that arrives while packets are going out ends the session with reason 4 (5.10.3.2, figure C6); it was passed over. An abort says in its third byte whether its sender was the originator or the responder, and a received abort ends only the session its sender had that role in (5.10.3.4, figure 14); the byte was sent as FFh and both sessions were ended. An acknowledgement that arrives before the last packet has gone is passed over (5.10.3.3); it ended the session |
| 2026-11-16 | J1939: the extended transport protocol is left as it was, without repair of a missing packet and with its abort message unchanged, because its standard, ISO 11783-3, was not at hand; only SAE J1939-21 was |
| 2026-11-16 | J1939: a notice for each data packet offset of the extended protocol (`RX_DPO`), with the number of bytes that have arrived in every notice, as the Linux kernel's J1939 documentation describes `J1939_EE_INFO_RX_DPO` and `J1939_NLA_BYTES_ACKED`. A priority for one message in the C API (`dcan_j1939_sendto_prio`) as well; the kernel's documentation describes a priority per socket only, so this one has no Linux counterpart to compare with. Protocol version 6 |
| 2026-11-16 | J1939: where SAE J1939-21 and Linux differ, the standard is followed. Linux's stack (kernel 6.8, can-utils 2023.03) was watched on a virtual interface in a virtual machine, with the other node played frame by frame. As a receiver it does not ask again for a missing packet: it sends an abort with reason 3 once 750 ms have passed after the last packet. As a sender it sends packets again when asked, from whatever packet the clear-to-send names (before the last block and beyond the next packet too), and after sending them again it sends an abort with reason 5 at once; it ends a session on an acknowledgement that comes before its last packet; its aborts carry FFh in the third byte; and it sends the transport protocol's own frames at the message's priority, not at 7. So a Linux sender that is asked for a packet again delivers the message and reports it as failed, which the run between the two stacks on one bus the same day showed (see the hardware validation log). Linux does accept an abort that carries the sender's role |
| 2026-11-16 | The J1939 tools (`j1939acd`, `j1939spy`, `j1939cat`, `j1939sr`, `testj1939`) are written from their usage texts, from SAE J1939-81 (April 2025) for address claiming, and from what can-utils 2023.03 was seen to print and to send on Linux 6.8, never from its source. Where the original prints Linux system calls (`-v`), does something that looks like a fault (`testj1939 -p=3` setting priority 0, `j1939spy` not filtering by a parameter group given alone, `j1939sr` sending without a parameter group), or cannot be had here (the `TX ENQ` progress lines of `j1939cat`), the tools differ, and tools.md says how |
| 2026-11-16 | `j1939acd` follows SAE J1939-81, 5.9, with the original's choices where the standard leaves them open: it asks for the claims of others and waits 1.25 s before its own; it takes a free address before it contends for one; it takes over a claim another node makes in its NAME; told to end, it sends a cannot claim address message and keeps the address in its cache file. The random delay after a bus collision of two claims (5.9.14) is not done: the adapters repeat frames by themselves |
| 2026-11-16 | J1939 stack, for address claiming: a NAME without an address may send a request for address claimed from the null address (SAE J1939-81, 5.9.3); when a NAME loses its address, its sessions end without an abort message (5.9.10); and a message carries its sender's NAME only once the claim has stood for 250 ms, which is what Linux was seen to do |
| 2026-11-16 | J1939: the transport protocols' own frames (request to send, broadcast announce, data, abort) go out at the message's priority, and a receiver answers at the priority the sender's frames came with. They went out at 7, which SAE J1939-21 gives as their default, so the priority of a long message was neither on the bus nor known to its receiver. Linux does as darwinCAN does now |
| 2026-11-16 | A received frame says whether a program on this machine sent it (`RxFrame::local`, `DCAN_RX_LOCAL`), as `MSG_DONTROUTE` does on Linux. `candump -x` needs it for its TX and RX, and the Python bus uses it for `is_rx`, which python-can's `socketcan` interface sets from `MSG_DONTROUTE`; before, `is_rx` was False for the bus's own frames only. Protocol version 7. Delivery latency on a virtual interface was measured before and after, six runs each, twice: medians of 53 to 94 µs before and 54 to 98 µs after, 99th percentiles of 171 to 210 µs before and 182 to 220 µs after |
| 2026-11-16 | CAN FD frames are written in log notation with the CAN FD bit in the flags digit (`##4` to `##7`), as can-utils has written them since 2023, and read with or without it. `cangen -v` keeps the digit without that bit, as the original prints the frames it made |
| 2026-11-16 | Of the options that were refused: `candump -x`, `-c`, `-i`, `-S`, `-d` and `-D`, `canplayer -i` and `cangen -a` are done. `candump -r` stays refused because there is no socket buffer to size; `-8` in `candump` and `cangen` because a raw DLC above 8 would have to pass through the frame type, the wire and every backend, for little use; `cangen -t` because nothing here sends a frame at a time set in advance; and the CAN XL options because CAN XL is not planned |
| 2026-11-16 | `cansniffer` and `isotpdump` are written from their usage texts and from what can-utils 2023.03 writes for given frames. The names `isotpdump -u` prints are those of ISO 14229-1; all 256 service identifiers and all 256 negative response codes were run through both programs and print the same |
| 2026-11-16 | The daemon limits the message data it holds in bytes. One connection may have 128 MiB of ISO-TP and J1939 messages waiting to be sent and 128 MiB waiting to be read, and always one message of either; all connections together 1 GiB (`--memory-limit`), half of it kept for sending. A send beyond that waits, as on a Linux socket whose buffer is full, so that a program that sends an image as many long messages in a loop runs at the speed of the bus and sees no error; a message for a client that does not read is dropped, as frames are. A long message is counted when its header arrives and before the rest is read. Frames are not counted and nothing is added to the frame path |
| 2026-11-16 | A client with nothing waiting always gets its next message, although that lets what waits for all clients go above its limit by one message a client. Without it, a client that read everything it was sent lost a message because others had filled the shared room, which a test showed |
| 2026-11-16 | The daemon takes blocks of a megabyte or more from the system with `mmap` and gives them back when they are freed. With the system allocator alone, three J1939 messages of 117 MB that nobody received left the daemon at 458 MB, with 82 KB in use: macOS 26 keeps freed large blocks. `malloc_zone_pressure_relief` did not release them. The setting `MallocLargeCache=0` did, but `man malloc` does not list it, so it is not relied on. With the daemon's own allocator it holds about 120 MB while such a message is in it and 7 MB afterwards |
| 2026-11-16 | A changelog (`CHANGELOG.md`) is kept from version 0.1.0 on, written for someone who uses a release and not for someone who works on the code. The README states the two licences in one line under its opening, as well as in its last section: the repository holds three licence files, and a reader who sees only one of them named beside the repository would take the daemon for permissively licensed |
| 2026-11-17 | The Kvaser backend tries for up to five seconds to take over an adapter that the system says another program has, where it tried once. A web browser opens each USB device as it is plugged in, and the adapter was left unattached in two of three plug-ins with one running. Only this backend waits, because only it has to select a USB configuration, which needs the device to itself; the PEAK backends claim an interface, which the browser does not hold. Five seconds is a guess: the device was free again within the time it took to look |
